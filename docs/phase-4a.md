# Phase 4A diagram integrations

`POST /api/v1/integrations/inventory-deductions` accepts a bearer JWT for Admin or Management, a printable ASCII `Idempotency-Key` header of 1–128 characters, and a JSON body such as `{"externalReference":"order-42-line-1","warehouseId":1,"itemId":2,"quantity":2}`. A dedicated Management account can use external login (`sessionMode=external`) as an independent HTTP client. The external reference is a stable source order-line identifier; the idempotency key is **not** an authentication key. Use the same key for unknown-success retries.

The key is unique per authenticated caller. Identical retries return the original `deductionId` and `resultQuantity` with `replayed:true`; changed payload with the same key returns 409 `idempotency_conflict`. The SQLite transaction conditionally reduces current stock only when at least one unit remains and inserts the successful deduction record before commit. Wrong warehouse/item returns 404; insufficient stock returns 409 `insufficient_stock`. Successful keys are retained with inventory history, without expiry. CRUD still uses `If-Match`; this delta operation does not. The caller should use a stable key and avoid automatically retrying with a new key after a timeout.

`POST /api/v1/supplier-orders` lets Admin/Management manually prepare a request with `warehouseId`, `itemId`, positive `requestedQuantity` and `supplierDestination`. The matching outbox entry is inserted in the same transaction. `GET /api/v1/supplier-orders` gives authenticated roles 10-row pages with `Pending`, `Sent` or `Failed`. A five-second worker dispatches due entries using the local adapter, which logs only the stable message ID; no supplier is contacted. Failures retry after exponential delays of 5, 10, 20, 40 seconds, up to five attempts (capped at 300 seconds). A message ID remains stable across attempts. This is at-least-once dispatch; a future live provider must deduplicate by ID where supported. `Sent` means local recording only. No low-stock automation or procurement approval is implied.

The web print report loads every warehouse and item page before enabling print, with English/Arabic resources and RTL. Browser print-preview and accessibility acceptance continue in Phase 5. Live supplier email/HTTP delivery remains unconfigured pending explicit recipient/channel/credential/cost and test-send authorization in Phase 8.

SQLite integration tests cover successful and replayed deductions, changed-key conflict, insufficient stock, wrong warehouse, simultaneous distinct orders, insert-failure rollback, supplier outbox creation, failed delivery, retry and duplicate dispatch. The web suite covers full multi-page report loading, print invocation and supplier-order roles/form. Phase 5 extends this with independent-client and browser acceptance against running services.
