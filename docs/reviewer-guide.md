# Assessment reviewer guide

The public source is in two repositories: [Happy Inventory API](https://github.com/Anas-Abukhadir97/happy-inventory-api) and [Happy Inventory Web](https://github.com/Anas-Abukhadir97/happy-inventory-web). Public read links require no invitation. The API repository owns the [requirements matrix](requirements.md), [architecture](architecture.md), [decisions](decisions.md), [backlog](backlog.md), [OpenAPI contract](contracts/openapi.v1.json), [tested image pair](../releases/phase-6-tested.json) and [Phase 6 recovery evidence](phase-6.md). The web repository provides [English/Arabic report screenshots](https://github.com/Anas-Abukhadir97/happy-inventory-web/blob/main/docs/phase-7.md).

## Clean local run

Install .NET SDK 10.0.401 or a compatible 10.0 patch, Node 24.14.1, Python 3 and Git. Clone the repositories as sibling directories named `backend` and `frontend`. In `backend/`, run `dotnet restore HappyInventory.sln --locked-mode` and `dotnet run --project src/HappyInventory.Api --launch-profile http`. In a second terminal, run `npm ci` and `npm run dev` from `frontend/`, then open `https://localhost:5173`. Vite's development certificate needs local trust. Sign in with the **Development-only** `admin@happywarehouse.com` / `P@ssw0rd` seed. Do not use it in Production. Swagger is separately available on loopback at `http://localhost:5081/swagger`; the API is at `http://localhost:5080` for local development.

The complete clean-checkout checks are in each README. The API sequence is locked restore, contract generation/validation, Release build, format verification and `dotnet test`. The web sequence is `npm ci`, contract check, lint, typecheck, formatting, coverage and production build. Its browser E2E test uses a fresh temporary SQLite database and Chromium; see the web README for prerequisites. Hosted CI runs these checks, builds both images independently, and exercises the pulled digest-pinned pair with restart and SQLite backup/restore. The latest main-branch workflow results are under each repository's **Actions** tab.

## Assessment walkthrough

1. Sign in as the Development admin. Create warehouses in different countries/cities and items. The list caps each page at 10; the print report loads all pages. Try duplicate active item names and quantity zero to see database-backed validation.
2. Open the dashboard and confirm distinct item count and total quantity, including an empty warehouse. View the full English and Arabic report. The [web screenshots](https://github.com/Anas-Abukhadir97/happy-inventory-web/blob/main/docs/phase-7.md) use isolated fixture data with 12 items.
3. As Admin, create `Management` and `Auditor` accounts and inspect the Admin-only log viewer. Management can write inventory but cannot manage users or read logs. Auditor can read inventory/dashboard/report but cannot mutate. Server authorization returns 403 even if a client bypasses the UI.
4. An independent HTTP client can POST `/api/v1/auth/login` with `{"email":"admin@happywarehouse.com","password":"P@ssw0rd","sessionMode":"external"}` and use the returned access token as `Authorization: Bearer <token>`. It receives no refresh cookie. Use GET `/api/v1/warehouses`, POST a warehouse, then GET its `ETag` and PUT it with `If-Match: "<version>"`. Missing/stale versions return 428/412.
5. For eCommerce deduction, POST `/api/v1/integrations/inventory-deductions` with `Idempotency-Key: order-42-line-1` and `{"externalReference":"order-42-line-1","warehouseId":1,"itemId":2,"quantity":2}`. Retry the identical key/payload to see `replayed:true` and no second decrement. Changing the payload under the same key returns 409. A deduction leaving zero stock also returns 409.
6. Create a manual supplier request from the web page or POST `/api/v1/supplier-orders`. Its outbox status may become `Sent`, which means only that the local adapter recorded delivery. No actual supplier is contacted.

IDs in examples must be replaced with IDs created in the reviewer's database. Browser login additionally requires exact HTTPS Origin and CSRF cookie/header; use the web app for that flow. The [versioned contract](contracts/openapi.v1.json) documents request and response shapes; Development Swagger shows runtime routes.

## Release artifacts and known limits

Run `python scripts/create_source_archives.py` from `backend/` after both checkouts are on clean `main`. It creates two source-only ZIP files and a SHA-256 manifest in the sibling `phase7-release/` directory. The archives contain tracked project files and the web fixture screenshots; they exclude `.git`, databases, logs, node modules, builds, secrets and original assessment attachments. The archive script does not email them. Both repository links above are already readable to reviewers; no collaborator invitation is implied. An Azure URL is unavailable until Phase 8 deployment and cost approval.

Current limits are deliberate: SQLite single instance; stock cannot reach zero under the assessment rule; supplier delivery is local-only; default country data is a bounded catalog; no public registration; no open-source license selected; browser accessibility automation does not replace manual assistive-technology review. The API contract remains `0.2.1-draft` until a runtime-schema reconciliation for a stable 1.0.0. Advanced exports, procurement, multi-currency, OAuth for machine clients and scale-out are in the backlog. No hosted Azure service, public TLS or rollback claim is made in Phase 7.
