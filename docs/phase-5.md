# Phase 5 integrated acceptance

The companion web repository's `npm run test:e2e` starts a real API and HTTPS web server against a fresh temporary SQLite database. Its independent Node HTTP client signs in with external sessions, creates warehouses, 12 items and role accounts, then checks deduction success/replay/conflicting key, minimum stock, wrong warehouse, two competing orders, unauthenticated and Auditor rejection, and invalidation of a disabled account's existing token. It also checks `If-Match` 428/412, Admin/Management/Auditor permissions and local supplier outbox delivery. The API's 40 SQLite integration tests additionally inject a deduction-record write failure and confirm that neither stock nor a successful idempotency record commits; they cover supplier failure/retry and duplicate dispatch.

Real Chromium checks browser login, full report pagination, English and Arabic RTL, local supplier status, Auditor read-only behavior, two-tab refresh, mobile width, and axe WCAG 2 A/AA and 2.1 AA serious/critical violations. Chromium generates A4 print PDFs in both languages; both were rendered and visually inspected for complete rows and legible layout. Temporary credentials and database are isolated to the test run. No supplier is contacted. The web CI executes this integrated run after building the companion API checkout.

The generated 0.2.1-draft OpenAPI adds request/replay/conflict examples and documents local-only supplier status. The health operation was implemented in Phase 6. Known scope limits: SQLite is single-instance, zero stock is rejected by assessment rule, live supplier delivery is unconfigured, and advanced exports/procurement remain future work. Automated axe checks do not replace a manual assistive-technology review.
